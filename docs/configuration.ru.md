# Gateway — Nginx с веб-панелью

Небольшой HTTP gateway в **одном Docker-контейнере**: Nginx обслуживает приложения, Python управляет настройками, статическая веб-панель работает на **8083**. Без базы данных, Node.js, внешних CDN и установки Python-пакетов. TLS/SSL не выпускается и не завершается: его обслуживает ваш внешний прокси.

## Запуск

```bash
docker compose up -d --build
docker compose logs gateway
```

Панель: **http://127.0.0.1:8083**. При первом запуске случайный пароль администратора выводится один раз в логах (`Gateway admin — initial password`). В панели его можно изменить кнопкой с замком внизу меню или в разделе защиты.

Чтобы задать начальный пароль самостоятельно:

```bash
cp .env.example .env
# В .env укажите GATEWAY_ADMIN_PASSWORD длиной не менее 12 символов.
docker compose up -d --build
```

`GATEWAY_ADMIN_PASSWORD` используется **только при создании** `/data/admin.json`. Изменение переменной после первого запуска не меняет существующий пароль. В `/data` хранится хеш PBKDF2, а не открытый пароль. Сессии действуют 12 часов и сбрасываются при перезапуске.

Gateway слушает **80**, панель **8083**. В Compose панель опубликована только на loopback хоста. Для сервера доступ к ней можно получить туннелем:

```bash
ssh -L 8083:127.0.0.1:8083 user@your-server
```

Если SSL-прокси занимает порт 80 **на этом же хосте**, замените публикацию gateway на `"127.0.0.1:8080:80"` и направьте SSL-прокси на `127.0.0.1:8080`. Либо подключите прокси к Docker-сети и отправляйте трафик на `gateway:80`; тогда публикация 80 на хосте не требуется. Для прокси на другом сервере укажите доступный адрес/порт gateway и ограничьте доступ к нему сетью или firewall.

## Dashboard и метрики

Раздел **«Обзор системы»** открывается после входа. Метрики, графики и статус Nginx поступают раз в секунду через один SSE-поток `/api/events`, без периодического опроса HTTP API. Поток также обновляет статус Nginx на остальных страницах панели. На скрытой вкладке соединение закрывается; при возвращении открывается снова. Кнопка «Обновить» переподключает поток. При потере связи остаётся предыдущий снимок с явным предупреждением и временем обновления; переподключение выполняется автоматически с задержкой от 1 до 15 секунд. Если данные не поступают 15 секунд, соединение также восстанавливается.

Сервер собирает один общий снимок для всех подписчиков. Доступны до 16 одновременных потоков, остальные обработчики остаются свободными для входа, настройки и health checks. Очередь снимков не накапливается: медленный клиент получает последнюю версию. После переподключения приходит полный актуальный снимок; отдельного журнала SSE-событий нет. Авторизация проверяется перед отправкой обновлений, поэтому выход, смена пароля и истечение сессии прекращают доступ к потоку.

Если панель размещена за внешним прокси, отключите буферизацию для `/api/events` и разрешите долгие HTTP-ответы. Endpoint возвращает `Content-Type: text/event-stream`, `Cache-Control: no-cache, no-store, no-transform` и `X-Accel-Buffering: no`. Формат событий соответствует [стандарту SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html).

| Показатель | Как считается |
|:--|:--|
| Запросы и график | Завершённые HTTP-запросы к gateway; до 90 интервалов по 10 секунд. Последний интервал ещё заполняется |
| RPS | Число запросов в последнем полностью собранном 10-секундном интервале / 10 |
| Ошибки сервера | Ответы 5xx и их доля среди всех запросов. 4xx показаны отдельно |
| Время ответа | Nginx `$request_time`: включая чтение запроса и передачу ответа клиенту. WebSocket учитывается после закрытия |
| p95 | Приблизительный перцентиль по гистограмме; верхняя граница соответствующего диапазона, ограниченная максимальным измерением |
| Кеш | HIT / (HIT + MISS + EXPIRED + STALE + UPDATING + REVALIDATED). BYPASS и маршруты без кеша исключены |
| Передано | Тело ответа, отправленное клиенту; без HTTP-заголовков |
| Лимиты gateway | Запросы с `REJECTED` в `$limit_req_status` или `$limit_conn_status`; ответ 429 от upstream не считается срабатыванием лимита gateway |
| Соединения | Nginx `stub_status`: чтение, запись и keep-alive. Соединение самого запроса статистики вычитается; другие одновременные служебные соединения могут присутствовать |

Данные хранятся только в RAM текущего процесса и сбрасываются при его перезапуске. Интервалы округляются до 10 секунд, поэтому доступный период может быть немного короче 15 минут. Nginx reload сохраняет собранную историю. Dashboard показывает время начала сбора, нулевой трафик и отсутствие измерений задержки/кеша без подстановки демонстрационных значений.

Nginx передаёт минимальные JSON-события через локальный Unix datagram socket `/run/gateway/metrics.sock`. Не собираются реальные URL, query string, клиентские IP, заголовки и тела запросов: только настроенный `server_name`, настроенный путь маршрута, код, длительность, размер и результат кеша/лимитов. Неизвестные Host объединяются в одну строку. Число доменов в памяти ограничено 128 плюс группа остальных; журнал ошибок — 30 записей. Обычные stdout/stderr-логи Nginx остаются прежними.

Передача датаграмм работает без гарантии доставки: при перегрузке часть событий может быть потеряна. Dashboard предназначен для оперативного наблюдения, а не биллинга или аудита. Показатели отражают наблюдаемые ответы, а не активные health-checks всех upstream; отсутствие ошибок без трафика не подтверждает доступность приложений.

`/api/events` и совместимый endpoint для разового снимка `/api/dashboard` требуют входа в админку. Служебные `/generation` и `/status` слушают только loopback внутри контейнера; их запросы не учитываются в трафике. При обновлении версии сервиса Nginx-конфигурация заново генерируется **из действующих настроек**, проверяется через `nginx -t` и сохраняется новой версией. Неприменённый черновик остаётся отдельным.

Для собственного Nginx требуется модуль `http_stub_status` (сборка с `--with-http_stub_status_module`); в используемом Docker-образе он уже включён. Описание источников: [Nginx syslog](https://nginx.org/en/docs/syslog.html), [stub_status](https://nginx.org/en/docs/http/ngx_http_stub_status_module.html).

## Docker socket и выбор контейнеров

В разделе **Docker** задаются путь к Unix socket и, при необходимости, имя/ID самого gateway. Настройки сохраняются отдельно в `/data/docker.json` с правами 0600 и переживают перезапуск. Подключение отключено по умолчанию; включение или отключение discovery не изменяет действующие маршруты. Gateway использует Python stdlib, без Docker CLI или SDK внутри образа.

### Подключение socket

```bash
# Готовый образ
docker compose -f compose.ghcr.yaml -f compose.docker.yaml up -d

# Или локальная сборка
docker compose -f compose.yaml -f compose.docker.yaml up -d --build
```

Overlay монтирует `${DOCKER_SOCKET_PATH:-/var/run/docker.sock}` с хоста в `/var/run/docker.sock` контейнера. Для rootless Docker можно указать в `.env` `DOCKER_SOCKET_PATH=/run/user/1000/docker.sock`. Несуществующий путь не создаётся автоматически как каталог. Веб-поле **«Путь к socket внутри Gateway»** относится к пути внутри контейнера, а не пути на хосте. При использовании overlay этот путь остаётся `/var/run/docker.sock`.

В панели нажмите **«Подключить Docker»**. Стандартный Docker hostname позволяет автоматически определить контейнер gateway и его сети. Если вы задали собственный `hostname`, укажите настоящее имя/ID gateway в панели или первоначально через `GATEWAY_DOCKER_CONTAINER`. Для запуска без overlay путь по умолчанию можно задать через `GATEWAY_DOCKER_SOCKET`; сохранённые настройки панели имеют приоритет над переменными окружения.

Процесс Gateway должен иметь доступ к socket. В стандартном образе управление запускается от root; при собственном непривилегированном запуске выдайте доступ через соответствующую группу/GID socket. Делать socket общедоступным через `chmod 666` не требуется.

### Сети и цели маршрута

Gateway и приложения должны быть подключены к общей **пользовательской сети**. Основной Compose создаёт сеть `nginx-gateway`. Для приложения из другого Compose-проекта:

```yaml
services:
  backend:
    image: your-backend:latest
    expose:
      - "8000"
    networks:
      - gateway
networks:
  gateway:
    external: true
    name: nginx-gateway
```

Либо подключите уже работающий контейнер: `docker network connect nginx-gateway backend-1`. Панель читает состояние Docker, но сама не подключает контейнеры к сетям и не меняет их настройки.

В новом домене или в **Маршрут → Серверы → Выбрать из Docker** отметьте один или несколько контейнеров. Выберите TCP-порт; если приложение не объявило его, используйте ручной ввод. Публиковать порт на хост для общей сети не нужно. Выберите, добавить цели к текущим или заменить список. Повторный выбор той же пары адрес/порт не создаёт дубликат; максимум — 32 цели маршрута. После выбора можно менять веса, backup и алгоритм балансировки обычным способом. До сохранения маршрута и «Применить» рабочий Nginx не меняется.

| Запуск / сеть | Сохранённая цель |
|:--|:--|
| Общая пользовательская сеть с IPv4 | Имя Docker-контейнера и внутренний TCP-порт |
| Общий стандартный `bridge` или только IPv6 | Текущий IP и внутренний порт; IP может измениться при пересоздании |
| Gateway вне контейнера, локальный Docker | Адрес привязки опубликованного порта хоста; wildcard заменяется loopback |
| Нет общей сети / остановлен / сам gateway | Выбор недоступен с пояснением причины |

Для Docker-имён используйте resolver `127.0.0.11` в настройках Gateway. Nginx обновляет IP через встроенный DNS Docker (`valid=10s`). Пересоздание контейнера с **тем же именем** не требует правки маршрута. Переименование или создание новых реплик требует повторного выбора/добавления целей. `IP hash`, веса и резерв работают так же, как для ручных upstream. Container names с `_` поддерживаются; правила проверки публичных доменов не ослаблены.

Discovery показывает до 500 последних контейнеров, позволяет искать по имени, образу и Compose-сервису, фильтровать сети. «Можно выбрать» означает наличие подходящего сетевого адреса и запущенный процесс; это не проверка HTTP-доступности. Gateway остаётся HTTP-прокси: TCP-порт базы данных или UDP-сервиса не станет HTTP-приложением. Автоматические health-checks, управление контейнерами, удалённый Docker TCP/SSH endpoint и автоматическое масштабирование списка целей не реализованы. В режиме локального запуска предполагается daemon на том же хосте, а не перенаправленный socket удалённого сервера.

### Доступ и ограничения

Все запросы к `/api/docker` требуют входа; сохранение подключения защищено CSRF и проверкой версии настроек. Клиент выполняет только фиксированные GET: `/version`, список контейнеров и inspect самого gateway. В браузер не передаются переменные окружения, mounts, произвольные labels, команды или полный inspect. Ошибка Docker не останавливает проксирование; сохранённые цели продолжают работать независимо от discovery.

Сам socket предоставляет привилегированный доступ к Docker daemon и потенциально к хосту. Bind mount `read_only: true` защищает файловую точку монтирования, но не запрещает команды через Docker API. Поэтому подключайте socket только к доверенной панели и ограничивайте доступ к админке. Источники: [Docker — защита socket](https://docs.docker.com/engine/security/protect-access/), [пользовательские сети и DNS](https://docs.docker.com/engine/network/drivers/bridge/).

## Пример `example.com`

В пустой панели нажмите **«Пример example.com»**. Он создаёт черновик:

| Входящий адрес | Серверы | Поведение |
| --- | --- | --- |
| `example.com/` | `frontend-1:3000`, `frontend-2:3000` | Корневой frontend, round robin |
| `example.com/api` | `backend-1:8000`, `backend-2:8000` | Least connections; `/api/users` → `/users` |
| `example.com/s3` | `minio:9000` | Сохранение пути; кеш выключен; тело до 1 GiB |

Замените примерные адреса на реальные имена контейнеров или IP, затем нажмите **«Применить»**. Домен направляйте на свой SSL-прокси, который передаст запрос gateway с исходным `Host`.

Имена upstream — это DNS-имена или IP без `http://` и без пути. Порт задаётся отдельно. Соединения с upstream — HTTP; upstream по HTTPS, TCP/UDP и gRPC в этой версии не поддерживаются.

Контейнеры приложений должны находиться в доступной сети. Compose создаёт сеть `nginx-gateway`. Для уже запущенного контейнера:

```bash
docker network connect nginx-gateway frontend-1
```

Для другого Compose-проекта:

```yaml
services:
  frontend-1:
    image: your-frontend
    networks: [gateway]
networks:
  gateway:
    external: true
    name: nginx-gateway
```

`localhost` в настройке upstream — **сам gateway-контейнер**, а не Docker-хост. Имена контейнеров разрешаются через `127.0.0.11` и обновляются динамически. Отсутствие приложения в момент запуска не мешает запустить gateway; запрос к недоступному upstream завершится ошибкой 502.

## Маршруты и балансировка

- Несколько доменов, отдельное включение/выключение каждого.
- Пути `/`, `/api`, `/api/v1`, `/s3`. `/api` охватывает `/api` и `/api/...`, но не `/apix`.
- **Убирать префикс**: `/api/users?q=1` → `/users?q=1`. Без этой опции путь передаётся без изменений.
- Несколько серверов, веса, **round robin**, **least connections**, **IP hash**.
- Резервный сервер `backup` с round robin / least connections. Nginx не поддерживает backup с IP hash.
- Пассивное исключение недоступных upstream: `max_fails=3`, `fail_timeout=10s`, повтор на другой сервер при сетевой ошибке или 502/503/504. Для единственного сервера Nginx игнорирует пассивное исключение. Активных health probes приложений нет; зелёный индикатор панели показывает состояние самого Nginx.
- WebSocket, таймаут ответа, размер тела запроса на маршрут.

Панель настраивает перечисленные возможности через структурированные поля и показывает итоговый `nginx.conf`. Произвольные директивы и редактирование сырого конфига не поддерживаются: иначе панель не сможет надёжно валидировать и восстановить настройки.

## S3 и префикс `/s3`

Обычное HTTP-проксирование на `/s3` работает, если приложение принимает такой путь. **Универсально перенести стандартный S3 API под произвольный префикс нельзя**: SigV4 включает путь и `Host` в подпись. Удаление `/s3` может сделать подпись недействительной. При сохранении пути MinIO может интерпретировать `s3` как имя bucket, а не служебный префикс.

Для полноценного MinIO/S3 API обычно настройте отдельный домен, например `s3.example.com`, маршрут `/` → `minio:9000`, с сохранением пути и отключённым кешем. S3 SDK должен подписывать запросы для этого публичного endpoint; внешний SSL-прокси должен сохранять исходный `Host`. Для доступа к объектам существующего bucket `s3` вариант `/s3/...` может работать без удаления префикса. Поддержка конкретного SDK/хранилища требует проверки с ним.

## Лимиты и базовая защита

В разделе **«Защита и лимиты»**:

- общий лимит запросов с IP, суммарный по всем доменам/маршрутам; по умолчанию **20 r/s**, burst **40**;
- отдельный дополнительный лимит на маршрут; он действует **вместе** с общим;
- burst пропускается сразу (`nodelay`), превышение лимита возвращает **429**; это алгоритм Nginx leaky bucket, а не счётчик по календарным секундам;
- ограничение одновременных обрабатываемых запросов с IP, по умолчанию 50;
- размер тела запроса, по умолчанию 100 MiB; превышение — 413;
- запрет `.env`, `.git` и прочих скрытых файлов, кроме `.well-known`;
- запрещён TRACE; разрешены GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS;
- таймауты заголовков/тела, скрытие версии Nginx, `nosniff` и `Referrer-Policy`.

**За SSL-прокси обязательно настройте доверенные IP/CIDR.** Иначе Nginx будет считать источником сам прокси, и все пользователи разделят один лимит. Доверяйте только фактическому адресу/подсети вашего прокси. Прокси должен устанавливать корректные `X-Forwarded-For` и `X-Forwarded-Proto`. От недоверенных источников эти заголовки не используются для определения IP/схемы; приложение получает нормализованный адрес клиента. Сам gateway должен быть доступен только через ожидаемые точки входа, если требуется принудительный внешний TLS.

Панель имеет отдельный пароль, ограничение попыток входа, HttpOnly / SameSite-cookie, CSRF-проверку, запрет межсайтовых записей и встраивания во frame. При доступе к **панели** через HTTPS установите `GATEWAY_SECURE_COOKIE=true`. Без HTTPS эта настройка не позволит браузеру отправлять cookie.

Это базовая HTTP-защита, а не WAF или защита от объёмного DDoS. Для таких задач нужен внешний слой.

## Кеш

Включается отдельно на каждом маршруте; по умолчанию выключен. Общий размер — 1024 MiB, изменяется в разделе **«Кеширование»**.

- Кешируются GET/HEAD, ответы 200/301/302, с настраиваемым TTL.
- Учитываются `Cache-Control`, `Expires`, `Vary`, `Set-Cookie` upstream. TTL панели используется, когда upstream не задаёт собственное время кеширования.
- Запросы с `Authorization`, `Cookie`, `Upgrade`, `Cache-Control: no-cache/no-store`, а также параметрами `X-Amz-*`, `Signature`, `AWSAccessKeyId`, `token`, `access_token` обходят кеш.
- Ответы с `Set-Cookie` не сохраняются. Кеш включайте только для публичных данных: произвольные способы авторизации приложения панель распознать не может.
- Заголовок `X-Gateway-Cache`: `MISS`, `HIT`, `BYPASS` и стандартные состояния Nginx.
- Ключ включает исходный Host, внешнюю схему, полный URI с query и версию настроек маршрута. Изменённый upstream не получает старый кеш другого назначения.
- Файлы хранятся в `/cache`; неиспользованные записи удаляются через 60 минут. Лимит размера контролируется фоновым cache manager и может временно превышаться. Отдельной ручной purge-операции нет.

## Хранение, применение и откат

```text
/data/
  admin.json                  # соль и хеш пароля
  docker.json                 # необязательные настройки Docker discovery
  draft.json                  # сохранённый черновик
  active -> revisions/<id>    # атомарный указатель на действующую версию
  revisions/<id>/
    config.json               # настройки панели
    nginx.conf                # полная конфигурация Nginx
    meta.json                 # время создания и применения
/cache/                       # дисковый кеш Nginx
```

1. Изменения в редакторе ещё не сохранены на сервере.
2. **Сохранить** записывает JSON-черновик на диск, не меняя маршрутизацию.
3. **Применить** сохраняет черновик, создаёт новую версию, запускает `nginx -t`.
4. Только после успешной проверки атомарно переключается `active` и отправляется SIGHUP.
5. Служебный endpoint на **loopback 8084 внутри контейнера** подтверждает версию, которую обслуживают новые workers. Если reload не подтверждён, сервис возвращает предыдущую версию и повторно проверяет её.

Текущие соединения завершаются плавно; максимальное время жизни старых workers после reload — 30 секунд, поэтому длительные WebSocket-соединения могут потребовать переподключения. Проверка версии подтверждает загрузку конфига Nginx, но не доступность каждого upstream.

В истории хранятся 20 последних применённых версий. **«В черновик»** восстанавливает выбранную версию; **«Применить»** активирует её. После рестарта запускается именно действующая версия; неприменённый черновик сохраняется отдельно. При завершении Nginx завершается и контейнер, чтобы `restart: unless-stopped` восстановил сервис.

Экспорт/импорт JSON доступен на странице маршрутов. Экспорт включает текущие настройки редактора, без пароля и кеша. Для полной резервной копии сохраняйте volume `gateway-data`. Не запускайте `docker compose down -v`, если хотите сохранить настройки.

Для bind mount вместо именованных volumes можно использовать `./data:/data` и `./cache:/cache`. Каталог `/data` принадлежит пользователю процесса управления, имеет права 0700; JSON-файлы — 0600. В поставляемом образе процесс управления и master Nginx запускаются от root внутри контейнера, workers — непривилегированные. Docker socket нужен только для необязательного discovery; обычная маршрутизация работает без него.

## Разработка и проверки

Требуются Python 3.10+ и Nginx **1.28+** с модулями realip, rewrite и stub_status. В Docker они уже есть. Веб-интерфейс — обычные HTML/CSS/JS без сборки.

```bash
python3 -m unittest tests.test_config -v
node --check gateway/static/app.js
node --check gateway/static/dashboard.js
node --check gateway/static/docker.js
docker compose config --quiet

# Интеграционные тесты запускают настоящий nginx и временные HTTP upstream.
TEST_NGINX=/usr/sbin/nginx \
TEST_MIME_TYPES=/etc/nginx/mime.types \
python3 -m unittest discover -v
```

Если Nginx не установлен, интеграционные тесты будут отмечены как skipped. Можно проверить всё внутри образа с примонтированными тестами:

```bash
docker compose build
docker run --rm --entrypoint python3 \
  -v "$PWD/tests:/app/tests:ro" \
  local/nginx-gateway:latest -m unittest discover -v
```

Для локального запуска без Docker задайте `GATEWAY_DATA_DIR`, `GATEWAY_CACHE_DIR`, `GATEWAY_RUN_DIR` на доступные абсолютные пути; `NGINX_BIN` и `NGINX_MIME_TYPES` при нестандартной установке. Порты можно изменить через `GATEWAY_HTTP_PORT`, `GATEWAY_CONTROL_PORT`, `GATEWAY_ADMIN_PORT`, адрес панели — через `GATEWAY_ADMIN_BIND`. Затем `python3 -m gateway.main`. При изменении runtime-путей/портов после перезапуска создаётся проверенная версия конфига из действующих настроек.

Nginx использует два workers для быстрого старта; менеджер и панель не участвуют в передаче трафика приложений. При старте нет миграций базы, установки зависимостей и frontend build. Реальное время старта зависит от Docker-хоста; сборка/загрузка образа выполняется отдельно.

Семантика директив: [upstream и DNS](https://nginx.org/en/docs/http/ngx_http_upstream_module.html), [proxy и cache](https://nginx.org/en/docs/http/ngx_http_proxy_module.html), [rate limiting](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html), [real IP](https://nginx.org/en/docs/http/ngx_http_realip_module.html).
