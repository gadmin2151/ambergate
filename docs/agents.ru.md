# AmberGate Agent

[English](agents.md) · [README](../README.ru.md)

**Агент — отдельный Docker-контейнер на каждой удалённой машине.** Он читает локальный `docker.sock`, подключается к сетям приложений и сам открывает HTTPS/WSS-соединение с центральным AmberGate. Публиковать порты приложений и открывать входящий порт агента не требуется.

Трафик проходит так: клиент → ваш TLS-прокси → центральный Nginx → туннель → агент → приватный порт контейнера. Домены, пути, балансировка, кеш и ограничения остаются в центральном Nginx. Туннель передаёт HTTP потоково, включая загрузки, SSE и WebSocket приложений.

## Быстрое подключение: одна команда

1. В разделе **Общие настройки** один раз сохраните адрес центрального AmberGate. Домен `embergate.exemple.com` превратится в `https://embergate.exemple.com`. Ваш TLS-прокси должен направлять его на панель **8083**, а не на порт приложений 80.
2. Откройте **Агенты → Добавить агента**, задайте название машины и создайте агента.
3. Укажите существующую Docker-сеть приложений на этой машине. На вкладке **Docker run** уже будет **готовая команда в одну строку** с адресом центра и новым токеном. Нажмите **Копировать команду** и выполните её на Docker-машине.
4. Не закрывайте мастер: статус **Агент подключён** появится автоматически через SSE после успешного отчёта. На вкладке **Docker Compose** можно скачать готовый файл и запустить его командой `docker compose -f compose.agent.yaml up -d`.
5. Выберите контейнеры агента вручную в редакторе маршрута либо добавьте labels в приложения. Для labels включите режим **Предлагать изменения** или **Применять автоматически**. Одна настройка автоматизации labels действует для локального Docker и всех агентов; по умолчанию она выключена.

Пример команды — мастер сам подставляет ваш адрес и персональный токен:

```bash
docker run -d --name ambergate-agent --restart unless-stopped --init --read-only --tmpfs /tmp:size=16m,mode=1777 --network ambergate-apps --mount type=bind,source=/var/run/docker.sock,target=/var/run/docker.sock,readonly -e AMBERGATE_SERVER_URL=https://embergate.exemple.com -e AMBERGATE_AGENT_TOKEN='<AGENT_TOKEN>' ghcr.io/gadmin2151/ambergate-agent:latest
```

Сеть должна существовать и содержать приложения. Если она `internal: true`, подключите агент также к сети с исходящим доступом к центру. Один агент может состоять в нескольких сетях. Публиковать порты агента и приложений не нужно.

Команда и Compose содержат секретный токен, доступный только в мастере. Сохраните выбранный вариант и не публикуйте его в Git. Для скачанного файла можно ограничить доступ командой `chmod 600 compose.agent.yaml`. Если закрыли окно без сохранения, нажмите **Новый токен** — предыдущий будет отозван. При замене токена удалите старый контейнер `ambergate-agent` перед новой командой Docker run; для Compose замените файл и выполните `up -d`.

### Просто IP и подтверждение HTTP

В общих настройках можно ввести **`10.0.0.10`** без схемы. Панель предложит **`http://10.0.0.10:8083`** и покажет предупреждение: **токен агента и трафик приложений будут передаваться без шифрования**. Адрес сохранится только после кнопки **Понимаю риск. Разрешить HTTP**. При отмене прежние настройки сохраняются.

Также можно ввести `10.0.0.10:9000` или полный HTTP-адрес. После подтверждения в команду и Compose автоматически добавляется `AMBERGATE_AGENT_ALLOW_HTTP=true`. Разрешение привязано к этому адресу; для другого HTTP-адреса потребуется новое подтверждение. При HTTPS этот параметр не добавляется. Явный `https://IP` поддерживается с проверкой сертификата, но просто IP никогда не превращается в `https://IP` автоматически.

Общий адрес используется для новых команд запуска. Уже запущенные агенты нужно перенастроить на их машинах. Значение хранится локально в `/data/settings.json`, отдельно от черновиков и маршрутов Nginx.

Можно использовать [Compose из репозитория](../compose.agent.yaml) и приватный `.env`:

```dotenv
AMBERGATE_SERVER_URL=https://embergate.exemple.com
AMBERGATE_AGENT_TOKEN=REPLACE_WITH_YOUR_AGENT_TOKEN
AMBERGATE_AGENT_NETWORK=ambergate-apps
AMBERGATE_AGENT_ALLOW_HTTP=false
```

Запуск одной командой:

```bash
docker compose -f compose.agent.yaml up -d
```

Образ: `ghcr.io/gadmin2151/ambergate-agent:latest`, платформы amd64 и arm64. Центральный сервис и агент выпускаются вместе; используйте соответствующие версии.

## Labels и балансировка

```yaml
services:
  backend:
    image: your-backend:latest
    networks: [applications]
    labels:
      ambergate.route: "host=example.com; path=/api; port=3000; strip=true"
    # ports не нужен: 3000 — внутренний HTTP-порт приложения.

networks:
  applications:
    external: true
    name: ambergate-apps
```

Одинаковые `host`, `path` и параметры маршрута на разных машинах объединяют контейнеры в один балансировщик. Поддерживаются `weight`, `backup` и алгоритмы балансировки Nginx.

Чтобы добавить контейнеры в существующий ручной маршрут, задайте ему **Docker group**, например `app-api`, и используйте:

```yaml
labels:
  ambergate.route: "group=app-api; port=3000; weight=2"
```

[Полный пример приложения и агента](../examples/agent.compose.yaml). [Другие примеры labels](../examples/docker-labels.compose.yaml).

Агент использует приватные адреса Docker-сети: `via=host` здесь не поддерживается. Уберите `via` или укажите `via=network`. Агент должен быть подключён ко всем сетям с помеченными приложениями; менять сети или публиковать порты сам он не будет. Один агент может состоять в нескольких сетях.

## Выбор удалённых контейнеров в маршруте

Откройте **Маршруты → Добавить/изменить маршрут → Выбрать из Docker**. В поле **Источник контейнеров** вместо локального Docker выберите агента. Отметьте запущенные контейнеры, выберите внутренние HTTP-порты или укажите порт вручную. Нажмите **Добавить выбранные → Сохранить маршрут → Применить**. Labels, локальный Docker socket на центральном AmberGate и публикация портов приложений не нужны.

Для балансировки между машинами добавьте контейнеры первого агента, снова откройте выбор и переключитесь на другого агента. Оставьте **Заменить текущий список серверов** выключенным, чтобы сохранить уже добавленные цели. Локальные серверы и контейнеры разных агентов можно объединять в одном маршруте; вес и резервные цели работают как обычно.

В маршруте отображаются агент, имя контейнера и порт приложения. Трафик проходит через постоянный локальный порт центрального AmberGate и исходящий туннель агента. При пересоздании контейнера с прежним именем адрес обновится после следующего отчёта. Остановленный или удалённый контейнер станет недоступен, и Nginx сможет попробовать другую цель. Ручные маршруты работают и при выключенной автоматизации labels; выбор контейнера меняет Nginx только после применения маршрута.

**Для ручного выбора обновите ранее запущенные агенты.** Панель определяет старую версию и показывает объяснение. Для Compose выполните `docker compose -f compose.agent.yaml pull`, затем `docker compose -f compose.agent.yaml up -d`. Для Docker run создайте **Новый токен** в карточке агента и пересоздайте прежний контейнер новой командой из мастера. Сначала обновите центральный AmberGate.

Ручные подключения хранятся в `/data/agent-manual.json`, постоянные порты — в `/data/agent-ports.json`. Сохраняйте весь каталог `/data`: одного экспорта JSON маршрутов недостаточно для переноса туннельных портов на другую установку. Удалённые порты не переиспользуются для других приложений, чтобы старые версии конфигурации оставались безопасными. Общий лимит — 1024 сохранённых туннельных подключения.

## Внешний HTTPS-прокси

Сертификаты остаются в вашем TLS-прокси. Нужна поддержка WebSocket Upgrade и передача заголовка `Authorization`. Пример внутри существующего TLS server в Nginx:

```nginx
location / {
    proxy_pass http://10.0.0.10:8083;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 90s;
    proxy_send_timeout 90s;
    proxy_buffering off;
}
```

Замените IP центрального сервера. По умолчанию используется HTTPS. URL агента должен указывать на корень сайта: префиксы путей и перенаправления не поддерживаются. Если панель защищена SSO, разрешите `/api/agents/connect`, `/api/agents/tunnel/*` и `/api/agents/report` использовать встроенную авторизацию токеном, сохранив защиту остальных страниц. Токен агента не даёт доступ к административному API.

Для собственного CA смонтируйте PEM-файл в агент и задайте `AMBERGATE_AGENT_CA_FILE=/run/secrets/ca.pem`. Проверка сертификата и имени сервера остаётся включённой.

## Состояние и отключение

- Агент отправляет полный отчёт каждые 5 секунд; панель получает статус через **SSE**. Окно контейнеров показывает последний отчёт на момент открытия.
- В маршруты попадают запущенные контейнеры с корректными labels и общей сетью. Nginx учитывает ошибки upstream; статус Docker healthcheck сам по себе не исключает запущенный контейнер. Ошибки labels, неполный список или потеря Docker сохраняют последний корректный отчёт до истечения таймаута.
- В режиме **Авто** цели пропавшего агента удаляются при следующей синхронизации, не позже чем через 5 секунд после таймаута. Остальные агенты и ручные цели сохраняются. Пустой управляемый маршрут возвращает **503**.
- Режим **Предлагать** показывает изменения, а **Выключено** сохраняет конфигурацию. Разрыв самого туннеля сразу приводит к ошибке upstream, позволяя Nginx попробовать другой доступный сервер.
- Отключение, удаление или замена токена немедленно закрывают туннель и аннулируют старый токен. Новый токен нужно записать в Compose и перезапустить удалённый агент.
- После перезапуска центра агент переподключается автоматически. Локальные порты upstream сохраняются между запусками и пересозданием контейнера с тем же именем. Старые адреса не назначаются другим приложениям.
- В `/data` центра сохраняются хеши токенов, отчёты, принадлежность целей агентам и соответствия портов. Делайте резервную копию всего каталога. Сами токены храните отдельно на машинах агентов.

## Переменные и ограничения

| Переменная агента | Значение |
|---|---|
| `AMBERGATE_SERVER_URL` | Общий адрес панели; по умолчанию HTTPS |
| `AMBERGATE_AGENT_TOKEN` | Уникальный токен из панели |
| `AMBERGATE_AGENT_TOKEN_FILE` | Путь к смонтированному секрету; приоритет выше переменной токена |
| `AMBERGATE_DOCKER_SOCKET` | `/var/run/docker.sock` |
| `AMBERGATE_DOCKER_CONTAINER` | Имя/ID самого агента, если автоопределение по hostname недоступно |
| `AMBERGATE_AGENT_CA_FILE` | Необязательный PEM-файл собственного CA |
| `AMBERGATE_AGENT_INTERVAL` | 5 секунд, допустимо 2–30; интервал должен быть меньше таймаута |
| `AMBERGATE_AGENT_ALLOW_HTTP` | По умолчанию `false`; мастер добавляет `true` после явного подтверждения HTTP |

Текущие пределы: **32 агента**, **32 одновременных TCP-потока на агент**, **128 суммарно**, **500 контейнеров и 1 MiB на отчёт**, **1024 сохранённых соответствия целей туннеля**. В маршруте максимум 32 цели суммарно. Неактивные upstream keepalive закрываются через 5 секунд. Длительные SSE и WebSocket-соединения приложений занимают поток всё время работы.

Агент передаёт только метаданные контейнеров и маршрутные labels. Переменные окружения, mounts и посторонние labels не передаются. При этом доступ к Docker socket даёт привилегированный доступ к хосту: монтирование `:ro` само по себе не запрещает изменяющие операции Docker API. Используйте доверенные машины и храните токены как секреты.
